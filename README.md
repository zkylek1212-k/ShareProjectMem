# ShareProjectMem

**Cross-tool shared project memory for Claude Code, Codex and Antigravity.**

One git-versioned memory that all three agents load automatically — so switching machines or
switching agents never means re-explaining the project or re-scanning the repo.

> **Status**: the mechanism is fully tested on Windows/Git Bash and Linux/Docker.
> One assumption is not yet verified: whether Codex and Antigravity actually **obey** the
> instructions they load. Neither has a headless CLI to automate that check — a one-minute manual
> test is described in [`docs/implement.md`](docs/implement.md) §12.

## Why

You switch between machines and between agents. Every switch, the agent:

- doesn't know where you left off or what comes next
- re-scans the whole repo to "understand the project"
- redoes finished work, or reverses decisions you already made

This puts *the minimum reliable information the next agent needs to take the correct next step*
into the repository, and makes every agent pick it up at startup.

**Cost**: ~1,000 tokens per session. **Avoided**: 10,000–50,000 tokens of re-exploration each time.

---

## How it works: one source of truth, two delivery paths

`.project-memory/handoff.md` is the **only** file that carries mutable state. All three agents get
it at startup, but by different mechanisms — because only Claude Code can automatically *run a
command and inject its output*:

```
              .project-memory/handoff.md   ← single source of truth
                          │
        ┌─────────────────┴──────────────────┐
        │                                     │
   status.sh                          sync-entry-files.sh
   (prints tier-1 when run)           (generates into static files)
        │                                     │
   Claude Code                    Codex          Antigravity
   SessionStart hook          AGENTS.md      .agents/rules/
   runs it → injected          auto-loaded     auto-loaded
                                    ▲                ▲
                                    └── regenerated by git hook ──┘
                              pre-commit  (handoff changes → regenerate + stage)
                              post-merge  (after pull → refresh)
```

The `AUTO-MEMORY` block inside those entry files is **machine-generated**, marked do-not-edit, and
derived from `handoff.md` — never hand-copied, so it cannot drift.

## Support matrix

| Capability | Claude Code | Codex | Antigravity | Mechanism |
|---|:--:|:--:|:--:|---|
| **Memory loaded at startup** | ✅ automatic | ✅ automatic | ✅ automatic | SessionStart hook / generated block |
| Install | `/memory-init` | `install.sh` | `install.sh` | both paths work |
| Write the handoff | `/handoff` | entry-file instructions | entry-file instructions | update thresholds in `PROTOCOL.md` |
| **Block "code changed, memory didn't"** | ✅ | ✅ | ✅ | **git pre-commit (tool-agnostic)** |
| **Block secrets entering the repo** | ✅ | ✅ | ✅ | **git pre-commit (tool-agnostic)** |
| Cross-machine sync | ✅ | ✅ | ✅ | `status.sh` / `post-merge` |

> **The honest floor**: a hook can catch a *missing* handoff. It cannot catch a *lazy* one.
> Content quality still depends on the agent, and no tooling changes that.

## Install

### Claude Code

```bash
claude plugin marketplace add zkylek1212-k/ShareProjectMem
claude plugin install shared-project-memory
```

Then, in any project:

```
/memory-init
```

### Codex / Antigravity / by hand (no Claude Code required)

```bash
git clone https://github.com/zkylek1212-k/ShareProjectMem.git
bash ShareProjectMem/install.sh            # into the current repo
bash ShareProjectMem/install.sh /my/repo   # into a specific repo
```

Windows PowerShell:

```powershell
.\install.ps1
```

Both paths run the same `scripts/init-memory.sh`, produce identical results, and are
**idempotent — no existing file is ever overwritten**.

**Prerequisites**: git, bash (Git Bash on Windows), and a target folder that is already a git repo.

### Codex plugin

Install the repository marketplace and plugin:

```bash
codex plugin marketplace add zkylek1212-k/ShareProjectMem
codex plugin add shared-project-memory@shared-project-memory
```

Then explicitly invoke `$shared-project-memory` from the project you want to initialize. The
plugin does not initialize projects automatically and does not add an MCP server; the skill runs
the existing project-scoped installer after checking the Git repository and existing memory files.

## What gets created

```
.project-memory/
├── INDEX.md              # pure index, no mutable state          (tier 1)
├── handoff.md            # the baton; the only place state lives (tier 1)
├── STATE.md              # milestones and macro progress         (tier 2, on demand)
├── DECISIONS.md          # append-only decisions + quick index   (tier 2, on demand)
├── PROTOCOL.md           # the full protocol            (first visit / on demand)
├── status.sh             # startup script — any agent or human can run it
├── sync-entry-files.sh   # generates the handoff into the Codex/Antigravity entry files
├── commit-handoff.sh     # lets the agent commit memory by itself
└── archive/
CLAUDE.md                          # appended block, never overwrites your content
AGENTS.md                          # Codex entry (carries the AUTO-MEMORY block)
.agents/rules/shared-memory.md     # Antigravity entry (same)
.githooks/pre-commit               # tool-agnostic enforcement
.githooks/post-merge               # refresh entry files after a pull
.gitattributes                     # keeps .sh files LF
```

## Daily use

**Starting** — just give any of the three agents a task. The memory is already in context.
For the freshest copy including uncommitted work, any agent can run
`bash .project-memory/status.sh`.

**Finishing** — `/handoff` in Claude Code; the completion procedure in `AGENTS.md` elsewhere.
The agent writes the handoff and **commits it itself**. When the work doesn't meet the update
threshold (read-only questions, trivial explanations, no-change reviews) it writes **nothing** —
that churn is a cost, not diligence.

**On a new machine** — after cloning, run once:

```bash
git config core.hooksPath .githooks
```

(`core.hooksPath` is per-clone local config; committing `.githooks/` does not enable it.)

## Tiered loading — smaller context, no loss of fidelity

| Tier | Files | Loaded |
|---|---|---|
| Tier 1 | `INDEX.md`, `handoff.md` | **every session**, automatically |
| Tier 2 | `STATE.md`, `DECISIONS.md`, `PROTOCOL.md` | **on demand** |
| Archive | `archive/`, `SESSION_LOG.md` | never automatically |

Full fidelity always stays on disk and in git. The saving comes from **not eagerly loading** —
never from shortening the files. `INDEX.md` deliberately holds no mutable state (no commit hash,
no date, no status), so it can never drift out of step with `handoff.md`.

| Session type | tokens |
|---|--:|
| Read-only question | ~740 |
| Normal development | ~1,100 |
| Architecture work | ~1,620 |
| **Weighted average** | **~1,000** |

## Two switches

```bash
export MEM_AUTOSYNC=1   # fast-forward sync at startup   (default off: report only)
export MEM_AUTOPUSH=1   # push after the agent commits   (default off: commit only)
```

Working across machines, **turn both on** — then "finish on machine A, see it on machine B" needs
no manual step at all.

**`MEM_AUTOSYNC`** — three guards, all required: the switch is on, the working tree is clean, and
the local branch has no divergent commits. It uses `git pull --ff-only` only: a non-fast-forward
aborts and changes nothing, so it can never produce a conflict or a half-finished rebase.
`rebase`, `merge`, `reset` and force-push are **never** run automatically.

**`MEM_AUTOPUSH`** — on rejection (divergence) it **reports and stops; it never forces or resets**.
The commit itself is unaffected by this switch: memory is always committed, the switch only decides
whether it is pushed.

## Sync layer: GitHub is not required

All you strictly need is a local `git init`. A remote is only needed to work across machines, and
it does not have to be GitHub.

| Option | Suits |
|---|---|
| GitHub / GitLab private repo | personal projects; least setup |
| Bare repo on a NAS or network share | when the code can't leave the building |
| **Bare repo in OneDrive / Google Drive** | when you only want the cloud drive you already have |
| No remote at all | single machine; everything else still works |

### ⚠️ Never put a working repo (including `.git/`) inside a cloud-synced folder

Ordering is not guaranteed — a ref can arrive before the object it points at, giving you
`bad object`. There is no merge — the cloud picks a winner and the other machine's commits vanish
silently. Files On-Demand placeholders stall git mid-read. **These failures are silent and they
lose history.**

### ✅ Instead: put a *bare* repo in the cloud folder and use it as the remote

A bare repo is written **only during push and fetch** — short, discrete windows the sync client can
converge on — and you keep git's real conflict detection.

```bash
# once, on the first machine
git init --bare "D:/OneDrive/git-remotes/myproj.git"
cd /d/repos/myproj                          # working tree lives OUTSIDE the cloud folder
git remote add origin "D:/OneDrive/git-remotes/myproj.git"
git push -u origin HEAD

# on every other machine
git clone "D:/OneDrive/git-remotes/myproj.git" D:/repos/myproj
git config core.hooksPath .githooks
```

Mark that folder "Always keep on this device" (turn off Files On-Demand).

## Verified behaviour

Tested against throwaway repositories, passing on both Windows/Git Bash and Linux/Docker
(Alpine + busybox):

- scaffolding is idempotent — a second run skips everything, overwrites nothing
- `src/` changed but memory not staged → **commit blocked**
- code + memory together → passes
- `api_key: <long value>` added to memory → **commit blocked**
- a commit that *removes* an existing secret → **passes** (not falsely blocked)
- prose such as `Never store passwords, API keys` in memory → not flagged
- the Claude hook path and running `status.sh` directly → **byte-identical output**
- running the hook in a repo with no `.project-memory/` → **silent no-op, exit 0**
- after install, the entry files **already** contain the AUTO-MEMORY block
- committing an updated handoff → both entry files **regenerate and stage themselves into the same commit**
- `commit-handoff.sh` with `src/app.py` already staged → **commits only the memory files;
  `src/app.py` stays staged and uncommitted**
- full cross-machine loop: A writes the handoff → auto commit + push → B pulls →
  **the latest task is there at startup, with no manual step**
- a push rejected by divergence → **reported only; the remote is not force-overwritten and the
  local commit is not reset**
- a brand-new repo with zero commits → commits correctly

## Known limitations

- **A hook cannot judge quality.** It catches a missing handoff, not a lazy one.
- **Codex and Antigravity obedience is unverified on real runs.** Which files they *read* is
  confirmed — the strings `.agents/rules/*.md`, `AGENTS.md` and `GEMINI.md` appear in the shipped
  Antigravity binary — but whether they follow the instructions still needs a manual check.
- **`handoff.md` merge conflicts** can still happen when two machines commit concurrently. The
  resolution rule is documented, not automated.
- **Codex and Antigravity see a snapshot** taken at the last commit or pull, not uncommitted work
  in progress. Run `status.sh` for the live view.
- **The `pre-commit` file matcher leans embedded** (`firmware|drivers`, `c/cpp/h`). Trim it for a
  pure-software project.
- **Antigravity's `.agents/rules/` path may move between versions.** Re-check with a grep after an
  IDE upgrade — it takes 30 seconds; the method is in the docs.
